# Agent workflow remediation and verification

Apply both new Prisma migrations before starting updated workers. Simulation clients now carry a `simulationRunId`; documents and actions inherit ownership through `clientId`. Existing clients have no owner and are never selected by a simulation tick or run-specific purge. The API limits interactive runs to 1–1,000 clients and 1–365 simulated days; the separate load-test script may use larger synthetic cohorts.

`POST /api/simulation/runs` and legacy `POST /api/simulation/start` share one validated submission path. Successful responses use `{ data: { run, jobsEnqueued } }`. A failed submission marks its run `FAILED` and removes any queued jobs it can still retire. Completed batches have a unique `(runId, batchStart, clientStart)` marker so retries cannot increment progress again. A completed/failed run rejects a stale tick. `purgeSimulationData(runId)` only deletes rows owned by that run; callers must first stop or finish its jobs.

Mastra storage initialization is serialized across processes by a non-blocking PostgreSQL advisory-lock poll. Do not replace it with a blocking `pg_advisory_lock`: Mastra's `CREATE INDEX CONCURRENTLY` can wait on the lock waiter's virtual transaction ID. New workers should call `getCerebro()` or `ensureMastraStorageInitialized()` before processing model jobs.

Stage 0 onboarding can bootstrap by requesting its first Stage 1 document; only a successful request moves the client to Stage 1. The policy still denies skipping later stages. Action tools write their own ledger rows; the prompts now tell agents not to duplicate them with `logAction`. Denied cross-client document reads log a `DOCUMENT_ACCESS_DENIED` action with the attempted ID in `citedFields`, not a foreign document relationship. Resolved HITL timeout replays are no-ops.

Prompt versions in an existing database override source prompts. Run `node --import tsx scripts/stage-workflow-prompts.ts` to create and point **STAGING** to the revised prompt texts; this does not change **PRODUCTION**. Review the staged prompts and run scenario evaluations before a human-confirmed promotion through the existing prompt-ops API. Do not use `prisma/seeds/seed-prompt-versions.ts` on a production database just to deploy this change; that script resets both pointers.

Verification scripts require a disposable PostgreSQL database migrated with `npx prisma migrate deploy`. `scripts/verify-simulation-workflows.ts` also needs Redis and exercises actual route → queue → worker processing for two runs, duplicate batch completion, scoped purge, denied-access audit, and resolved-timeout replay. `scripts/verify-cold-storage.ts` can be started twice concurrently on a fresh database to test first-use schema initialization. `scripts/verify-live-agent-workflows.ts` uses OpenRouter, must run with `DRY_RUN=true`, and checks that an expired document produces an advisor alert and a fresh Stage 0 client receives a real `REQUEST_DOCUMENT` action and reaches Stage 1. Use a temporary key via environment variable and monitor its provider-side usage; never commit it.
